1System Overview

METRON is an AI application testing and evaluation platform. It automatically tests AI agents, chatbots, RAG pipelines, and multi-agent systems — checking whether they work correctly, are safe to use, and can handle real-world load.

You give METRON an endpoint (the URL of your AI system) and a description of what it does. METRON then runs a full test campaign — generating realistic users (personas), realistic questions and attack attempts (test prompts), sending them to your AI, scoring the responses, and delivering a clear health report with root-cause analysis.

In one sentence: METRON is an automated red-team + quality tester for AI systems that produces a single health score and a detailed breakdown of every failure.

Key Capabilities

  • Fully automated — no manual test scripts needed
  • Tests 6 dimensions: functional correctness, security, quality, performance, load, and RAG faithfulness
  • Generates realistic user personas with different expertise levels and intents (genuine, adversarial, edge-case)
  • Uses real attack datasets (AdvBench, HarmBench) for security testing
  • Produces a health score (0–100 %) with domain-aware weighting
  • Root cause analysis pinpoints why failures happened from a 133-point taxonomy
  • Works with any HTTP-accessible AI endpoint (chatbot, RAG, form-based, multi-agent)

3The 8-Stage Testing Pipeline

Every test run goes through the same numbered stages, in order. Each stage builds on the previous one. Progress is reported live to the UI as a percentage (0–100 %).

Stage 0
Application Profiling

Understands what the AI does, who uses it, and what its boundaries are.

Stage 1
Persona Generation

Creates realistic simulated users with different goals, expertise, and emotional states.

Stage 2
Test Generation

Writes functional, security, and quality test prompts tailored to each persona.

Stage 3
Conversation Execution

Sends every test prompt to your AI endpoint and records the responses.

Stage 4
Evaluation

Scores responses across all six test dimensions using specialist tools and LLM judges.

Stage 5
Aggregation

Combines all scores into per-class summaries and a single health score.

Stage 6
Feedback Loop

Analyses patterns in failures to surface systemic issues.

Stage 7
Report Generation

Produces the final JSON data and a downloadable HTML report.

Stage 8
Root Cause Analysis (RCA)

Maps failures to a 133-point taxonomy and identifies the most probable root causes.

3.1 Stage 0 — Application Profiling

Progress: 5–10 %

Before testing can begin, METRON needs to understand what your AI application does. It analyses the seed document you upload (a description, architecture diagram, or technical spec) and extracts:

  • Application type — chatbot, RAG pipeline, multi-agent, or form
  • Domain — finance, healthcare, legal, education, etc.
  • User types — who uses the system (e.g. "customer", "analyst", "admin")
  • Use cases — what tasks the system handles
  • Boundaries — what the system should and should not do
  • Technical attack surface — 24 categories including authentication type, tools the agent can call, data it can access, and output destinations (used to generate targeted security tests)
No document? If you don't upload a document, METRON builds the profile from the agent description and domain you type in the Configure form.

3.2 Stage 1 — Persona Generation

Progress: 10–18 %

Real AI systems are used by many different types of people. METRON simulates this diversity using the Fishbone method: it fills a coverage matrix of user archetypes across multiple dimensions:

DimensionValues
IntentGenuine, Adversarial, Edge-case
ExpertiseNovice, Intermediate, Expert
Emotional StateCalm, Frustrated, Urgent
Conversation StateSeeking, Clarifying, Escalating, Satisfied, Abandoned

Each persona gets a name, a background story, a goal, and example entry phrases. A coverage validator checks the persona set for gaps and adds up to 3 additional personas if any archetype is missing.

3.3 Stage 2 — Test Generation

Progress: 20–25 %

Three types of tests are generated:

  • Functional prompts — realistic questions each persona would genuinely ask. For RAG applications, these are grounded in the provided knowledge text.
  • Security / adversarial prompts — attack attempts generated for adversarial personas, covering jailbreaks, prompt injection, PII extraction, toxicity, and category-specific attacks drawn from the AdvBench and HarmBench golden datasets.
  • Quality criteria — domain-specific criteria that define what a good answer looks like (e.g. "answers should cite sources", "responses must not exceed 3 sentences").
Attack categories you can choose on the Configure page: Direct Jailbreak, Role-play Jailbreak, Prompt Injection, PII Extraction, Toxicity Elicitation, Bias Elicitation, Data Exfiltration, Instruction Override, System Prompt Leak, Off-topic Misuse.

3.4 Stage 3 — Conversation Execution

Progress: 28–58 %

Every test prompt is sent to your AI endpoint via the appropriate adapter. Responses and latency are recorded. The pipeline supports four adapter types:

AdapterUse case
ChatbotAdapterStandard request/response chatbot APIs
RAGAdapterRAG systems that return both an answer and retrieved context chunks
FormAdapterForm-filling or structured-input AI systems
MultiAgentAdapterMulti-agent systems that return an answer plus an execution trace

The conversation runner supports multi-turn exchanges (follow-up questions). For RAG mode, a separate ground truth stream sends your uploaded question-answer pairs directly to the endpoint and records correctness.

3.5 Stage 4 — Evaluation

Progress: 58–89 %

All three evaluation streams run in parallel. Each uses the best available tool for the job — specialist libraries are preferred over LLM-based scoring wherever possible to reduce cost and improve consistency.

See Section 4 for the full breakdown of what is tested and how each metric is scored.

3.6 Stage 5 — Aggregation

Progress: 90–93 %

All MetricResult objects are aggregated into summary statistics per test class (functional, security, quality, RAG, performance, load). A health score is calculated as a weighted average, where weights depend on the domain (e.g. medical/finance applications give more weight to security; education applications give more weight to quality). See Section 7 for the scoring model.

3.7 Stage 6 — Feedback Loop

Progress: runs after Stage 4

The feedback loop analyses patterns across all failing conversations. It looks for systemic issues such as: a particular persona type failing consistently, a specific attack category always succeeding, or a certain conversation length triggering errors. These insights feed into the RCA stage.

3.8 Stage 7 — Report Generation

Progress: 97–99 %

The aggregated report is serialised to JSON (stored in memory and SQLite) and to a standalone HTML report that can be downloaded from the Results page. The HTML report is self-contained — it includes all charts and tables and can be opened in any browser with no internet connection.

3.9 Stage 8 — Root Cause Analysis (RCA)

Progress: 94–96 %

RCA maps every failure signal to a 133-point failure taxonomy with 8 categories:

CategoryWhat it covers
C1 — AI/ModelHallucination, reasoning errors, context handling, model limitations
C2 — RAGRetrieval failures, chunking problems, context faithfulness
C3 — IntegrationAPI errors, tool call failures, adapter mismatches
C4 — SecurityPrompt injection vulnerabilities, PII leaks, bias, insufficient guardrails
C5 — LatencySlow response times, timeout errors, high p95 latency
C6 — TPM / Rate LimitsToken-per-minute exhaustion, 429 errors
C7 — DatabaseData retrieval errors, stale knowledge, missing records
C8 — OperationalInfrastructure failures, configuration errors, deployment issues

Each root cause is assigned a probability score based on how many relevant signals were observed. The top causes and their evidence are shown on the Results page. A per-prompt failure classifier also adds a taxonomy label to every individual failing test so you can drill down to exactly why each prompt failed.

4What METRON Tests

4.1 Functional Testing

Question: Does the AI do what it is supposed to do?

Functional tests send realistic user queries to the AI and score the responses for:

MetricWhat it measuresTool
Answer RelevancyIs the response actually relevant to the question?DeepEval AnswerRelevancyMetric
HallucinationDoes the AI invent facts that are not supported?DeepEval HallucinationMetric
UsefulnessIs the response genuinely helpful to the user's goal?LLM judge rubric
CompletenessDoes the response answer all parts of the question?LLM judge rubric
ConsistencyIs the response coherent and internally consistent?LLM judge rubric
Pass threshold: A functional test is marked as passing if its score is ≥ 0.50 (50 %). The overall functional pass rate is the percentage of tests that pass.

4.2 Security Testing

Question: Is the AI safe and resistant to attacks?

Security tests use adversarial personas to probe the AI for vulnerabilities. METRON uses dedicated specialist libraries — not LLM guessing — for the most critical checks:

MetricWhat it detectsTool
PII LeakageDoes the AI output personal data (names, emails, phone numbers, ID numbers)?Microsoft Presidio AnalyzerEngine
ToxicityDoes the AI produce harmful, offensive, or hateful content?Detoxify classifier (ML model)
Prompt InjectionCan an attacker hijack the AI's instructions via a crafted input?LLM Guard PromptInjection scanner
Bias & FairnessDoes the AI respond differently based on protected characteristics?DeepEval BiasMetric (Azure OpenAI)
Toxic Request RefusalDoes the AI refuse known-harmful requests (from HarmBench dataset)?Heuristic refusal check (40+ language patterns)
Attack ResistanceDoes the AI resist jailbreak attempts, role-play attacks, and instruction overrides?LLM judge rubric with sanitised attack context
Domain-aware PII: In HR, medical, legal, and finance domains, names and locations are expected in responses and are not flagged as PII leakage. METRON adjusts its sensitivity based on your AI's domain.

Security tests also include probes generated from the AdvBench and HarmBench golden attack datasets. These are real-world harmful prompts used by AI safety researchers.

4.3 Quality Testing

Question: Is the AI's output actually good?

Quality testing evaluates responses against domain-specific criteria generated in Stage 2. It uses G-Eval (DeepEval's LLM-based rubric evaluator) to score responses on criteria such as:

  • Factual accuracy
  • Clarity and conciseness
  • Appropriate tone for the domain
  • Citation / source attribution (for RAG systems)
  • Compliance with domain-specific standards (e.g. legal disclaimer presence)
Pass threshold: Quality tests use a higher threshold of 0.70 (70 %) because quality expectations are naturally higher than simple correctness.

4.4 Performance Testing

Question: How fast does the AI respond?

Performance testing sends a configurable number of sequential requests to your AI endpoint and measures response latency. Results include:

MetricDescription
Average LatencyMean response time across all requests (milliseconds)
Minimum LatencyFastest observed response time
Maximum LatencySlowest observed response time
Median Latency (p50)50th percentile — typical response time
p95 Latency95th percentile — worst-case response time for 95 % of requests
p99 Latency99th percentile — the very worst-case response time
Throughput (RPS)Requests processed per second
Error RatePercentage of requests that returned an error
Pass threshold: Performance passes if p95 latency ≤ 5,000 ms (5 seconds). This threshold can be adjusted in core/config.py.

4.5 Load Testing

Question: Can the AI handle many users at once?

Load testing uses Locust (an open-source load testing tool) to simulate many concurrent users hitting your AI endpoint simultaneously. You configure the number of concurrent users and test duration on the Configure page.

MetricDescription
Concurrent UsersNumber of simultaneous simulated users
Total RequestsHow many requests were sent in total
Requests Per SecondSustained throughput under load
Average Latency under LoadMean response time while under concurrent pressure
p95 Latency under LoadWorst-case for 95 % of requests under load
Error Rate under LoadPercentage of requests that failed under concurrent stress

A load test is considered passing if the error rate stays below 10 % and latency remains within acceptable bounds at the configured concurrency level.

4.6 RAG Evaluation

Question: Is the RAG system retrieving and using the right information?

When the application type is set to RAG, METRON runs an additional evaluation stream using the RAGAS framework. This checks the quality of the retrieval-augmented generation process itself — not just whether the final answer is correct.

MetricWhat it measures
FaithfulnessIs the answer supported by the retrieved context? (Detects hallucination from the model ignoring its context)
Answer RecallDoes the answer cover all the relevant information from the context?
Context PrecisionAre the retrieved context chunks actually relevant to the question?
Answer CorrectnessHow close is the answer to the ground truth answer you provided?

For Answer Correctness, you can upload a ground truth file (CSV or JSON) with question-answer pairs. METRON sends each question to your RAG endpoint and compares the response to the expected answer.

Ground truth file formats accepted:
CSV with columns: question, expected_answer (also accepts: query, answer, reference)
JSON as a list of objects or as a wrapper object with keys like test_cases, data, or qa_pairs

Endpoint Configuration

METRON connects to your AI endpoint via HTTP. You can configure:

  • Endpoint URL — the full URL to send test requests to
  • Request field — the JSON field name to put the test prompt in (e.g. message, query, input)
  • Response field — the JSON field name to read the AI's response from (e.g. answer, response, output)
  • Auth type — None, Bearer token, API Key, or Basic auth
  • Request template — optional JSON template for complex request bodies
  • Response trim marker — optional string marker to extract just the relevant part of the response

6LLM Provider Support

METRON uses a separate LLM provider to generate test prompts, act as an LLM judge, and run DeepEval metrics. This is distinct from your AI endpoint being tested — it is METRON's own intelligence engine.

ProviderModels UsedRate LimitBest For
NVIDIA NIM (Default) Llama 3.1 8B (fast) / 70B (judge) 40 RPM (free tier) Balanced quality; free tier; good starting point
Azure OpenAI GPT-4o 2,700 RPM / 450K TPM Highest quality judgements; large-scale runs
Groq Llama 3.1 8B (fast) / 3.3 70B (judge) 30 RPM (free tier) Very fast inference; free tier
Google Gemini Gemini 2.5 Flash 60 RPM (free tier) Fast; 1M tokens/day free
Automatic fallback: If the primary provider returns a rate-limit error (HTTP 429), METRON automatically retries with Groq's 70B model, then falls back to Groq's 8B model.

Task-specific model routing

METRON selects different model tiers for different tasks:

  • fast — persona generation, simple formatting tasks (uses smaller/cheaper model)
  • judge — scoring responses, LLM-based evaluation (uses largest/best model)
  • balanced — test prompt generation (uses best available model)

7Health Score & Scoring Model

What is the Health Score?

The Health Score is a single number from 0 to 100 % that summarises how well your AI performed across all test dimensions. A score of 100 % means every test passed. A score below 50 % means the system has significant issues and should not be deployed without fixes.

How it is calculated

The health score is a weighted average of the pass rates of each test class. The weights depend on your AI's domain because different domains have different risk profiles:

DomainFunctionalSecurityQualityPerformanceLoad
Finance / Banking35 %40 %10 %10 %5 %
Medical / Healthcare35 %45 %10 %8 %2 %
Legal35 %40 %15 %7 %3 %
E-commerce / Retail35 %20 %10 %20 %15 %
Education40 %15 %30 %10 %5 %
Customer Support40 %15 %15 %20 %10 %
Government30 %45 %15 %7 %3 %
General (default)40 %30 %10 %15 %5 %

9Security Architecture

Authentication

METRON uses AWS Cognito for user authentication. The frontend obtains a JWT Bearer token from Cognito after login. Every API request includes this token in the Authorization header. The backend validates the token on every request.

Data Isolation

  • Every run belongs to a specific user. The API returns HTTP 403 if you try to access another user's run or project.
  • API keys are never stored in the job store or the database. They are used for the duration of the pipeline and discarded.
  • The in-memory job store contains only status, progress, and results — no credentials.

Concurrency

A global semaphore limits METRON to 10 concurrent pipeline runs at once. Each run also has its own lock to prevent race conditions if multiple stages update the job store simultaneously.

Error Handling

Each evaluation stage runs independently. If one stage fails (e.g. DeepEval is not installed, or the RAG evaluator times out), the pipeline records a warning and continues with the remaining stages. A run only fails hard if the conversation execution stage itself cannot reach your AI endpoint.
